# 자율 트레이딩 에이전트 기획서 (Autonomous Trading Agent)

> 코드네임: **xdd** — News/Social 신호 기반 자율 매매 에이전트
> 문서 버전: v0.1 (기획 초안) · 작성일: 2026-07-13
> 상태: 기획 검토 단계 (코드 작성 전)

## 0. TL;DR

뉴스와 X·Reddit 등 실시간 커뮤니티 신호를 읽고, **스스로 가설을 세우고 검증한 뒤**
주식(및 확장 시 크립토)을 자율적으로 매매하는 에이전트다.

기존 매크로 봇과의 결정적 차이는 **"고정된 규칙(if-then)을 실행하는 것"이 아니라,
목표(수익률/리스크)를 주면 스스로 계획·행동·회고·학습하는 인지 루프를 가진다는 점**이다.

- **시드머니:** $10–20 (극소 자본. 초기엔 페이퍼 트레이딩 → 소액 실거래 순으로 검증)
- **핵심 철학:** 신호 → 가설 → 검증 → 사이징 → 실행 → 회고의 폐루프(closed-loop)
- **1차 목표:** "돈 버는 것"이 아니라 **"에이전트가 합리적 의사결정을 하고, 그 근거를 감사(audit) 가능하게 남기는 것"**

## 1. 비전 & 목표

### 1.1 비전
사람 트레이더가 하는 일 — 뉴스를 읽고, 커뮤니티 분위기를 감지하고, "이건 오르겠다/내리겠다"
가설을 세우고, 확신 정도에 따라 베팅 크기를 조절하고, 결과를 복기하는 —
전 과정을 자율적으로 수행하는 에이전트.

### 1.2 성공 기준 (단계별)
| 단계 | 목표 | 성공 지표 |
|------|------|-----------|
| **P0 검증** | 의사결정 품질 | 모든 매매에 근거·신뢰도·리스크가 로그로 남는가 |
| **P1 페이퍼** | 무손실 학습 | 페이퍼 트레이딩 4주, 벤치마크(SPY) 대비 리스크조정수익(Sharpe) |
| **P2 소액 실거래** | 생존 | $10–20으로 30일 생존 + 최대낙폭(MDD) 통제 |
| **P3 확장** | 반복 가능성 | 전략이 통계적으로 유의미한 엣지를 보이는가 |

### 1.3 명시적 비목표 (Non-Goals)
- ❌ 고빈도 매매(HFT) — 지연·수수료 구조상 소액 자본과 상극
- ❌ "무조건 수익 보장" — 시장은 예측 불가. 우리는 **기대값과 리스크**를 관리할 뿐
- ❌ 시세조작·펌프앤덤프 신호 추종 — 규제 위반·손실의 지름길, 명시적으로 필터링
- ❌ 레버리지/옵션 (초기 범위 제외, P3 이후 논의)

## 2. 핵심 차별점: "매크로 봇"이 아니라 "에이전트"

이 프로젝트의 존재 이유. 왜 이게 그냥 봇이 아닌가?

| 축 | 전통 매크로 봇 | 본 에이전트 |
|----|---------------|-------------|
| **의사결정** | 하드코딩된 규칙 (RSI<30 매수 등) | LLM 추론 + 가설 생성/검증 |
| **입력** | 정형 가격 데이터 | 비정형 뉴스·소셜 텍스트 + 가격 |
| **적응** | 규칙 수동 변경 | 회고(reflection)로 프롬프트·가중치 자기 조정 |
| **설명가능성** | "규칙이 그랬다" | 자연어 근거 체인 + 인용 출처 |
| **도구 사용** | 단일 API 호출 | 다중 툴 오케스트레이션 (검색·계산·백테스트) |
| **메모리** | 없음/상태만 | 단기(세션)+장기(교훈) 메모리 |

**핵심:** 에이전트는 "무엇을 살지"를 코드가 정하지 않는다.
에이전트가 **툴을 써서 스스로 조사하고, 판단하고, 그 판단을 검증**한 뒤 결정한다.

## 3. 에이전트 인지 아키텍처 (핵심)

전통적인 봇의 파이프라인이 아니라 **인지 루프(Cognitive Loop)** 로 설계한다.
OODA 루프(Observe–Orient–Decide–Act)에 회고를 더한 구조.

```
        ┌─────────────────────────────────────────────────────────┐
        │                    에이전트 인지 루프                      │
        │                                                           │
        │   ① OBSERVE          ② ORIENT           ③ DECIDE          │
        │  ┌──────────┐      ┌──────────┐      ┌──────────┐        │
        │  │ 신호 수집 │─────▶│ 가설 생성 │─────▶│ 사이징/  │        │
        │  │ (뉴스/소셜│      │ + 검증    │      │ 승인     │        │
        │  │  /가격)   │      │ (근거체인)│      │ (리스크) │        │
        │  └──────────┘      └──────────┘      └────┬─────┘        │
        │       ▲                                    │              │
        │       │            ⑤ REFLECT              ▼              │
        │  ┌────┴─────┐      ┌──────────┐      ④ ACT               │
        │  │ 장기메모리│◀─────│ 회고/교훈 │◀─────┌──────────┐       │
        │  │ (교훈DB) │      │ 추출     │      │ 주문 실행 │       │
        │  └──────────┘      └──────────┘      │ (브로커)  │       │
        │                                       └──────────┘       │
        └─────────────────────────────────────────────────────────┘
```

### 3.1 각 단계의 역할

**① OBSERVE (관찰)**
- 뉴스 API, X, Reddit, 가격 피드에서 신호 수집
- 노이즈 필터링: 봇/스팸/시세조작 의심 계정 제거
- 이벤트화: "TSLA 관련 급증하는 부정 감성" 같은 구조화된 이벤트로 변환

**② ORIENT (판단/가설)**
- 에이전트가 각 이벤트에 대해 **투자 가설**을 자연어로 생성
  - 예: "실적 서프라이즈 + 소셜 긍정 급증 → 단기 상승 모멘텀, 신뢰도 0.65"
- **자기 검증(self-critique):** 반대 근거를 스스로 찾게 함 (확증편향 방지)
- 신뢰도(confidence) + 예상 방향 + 예상 기간 + 리스크 요인 산출

**③ DECIDE (결정/사이징)**
- 리스크 엔진이 가설을 받아 **포지션 크기** 결정 (분수 켈리 등, §7)
- 하드 가드레일 통과 여부 확인 (단일 종목 한도, 총 노출 한도, 손절 등)
- **이 단계는 결정론적 코드가 최종 거부권을 가진다** — LLM이 아무리 확신해도 룰 위반이면 차단

**④ ACT (실행)**
- 브로커 API로 주문 (페이퍼/실거래)
- 체결 확인, 슬리피지 기록

**⑤ REFLECT (회고)**
- 포지션 종료 후 결과 vs 가설 비교
- "무엇이 맞았고 틀렸나" 교훈을 장기 메모리에 저장
- 반복되는 실수 패턴 → 프롬프트/가중치 조정 제안

### 3.2 멀티 에이전트 구성 (역할 분리)
단일 거대 프롬프트 대신 **전문화된 서브 에이전트**로 나눠 신뢰성·감사성 확보:

| 에이전트 | 책임 | 비유 |
|----------|------|------|
| **Analyst** (분석가) | 신호→가설 생성, 근거 조사 | 리서치 애널리스트 |
| **Skeptic** (회의론자) | 반대 근거 제시, 가설 공격 | 리스크 리뷰어 |
| **Risk Manager** (리스크) | 사이징, 가드레일, 최종 거부권 | 리스크 데스크 |
| **Trader** (실행) | 주문 라우팅, 체결 관리 | 실행 트레이더 |
| **Reviewer** (회고) | 사후 분석, 교훈 추출 | 포트폴리오 리뷰 |

> Analyst와 Skeptic을 분리하는 것이 핵심 안전장치다.
> 한 모델이 매수 근거를 만들면, 다른 모델이 반드시 반박하게 하여 과신을 억제한다.

## 4. 피처 리스트

### 4.1 MVP (P0–P1, 반드시 필요)

**데이터 수집**
- [ ] 뉴스 수집기 (금융 뉴스 API 1종 + RSS)
- [ ] X(트위터) 수집기 (키워드·계정 팔로우, 감성 태깅)
- [ ] Reddit 수집기 (r/stocks, r/wallstreetbets 등, 급증 감지)
- [ ] 실시간/지연 가격 피드 (브로커 API 기반)
- [ ] 스팸/봇/시세조작 신호 필터

**에이전트 코어**
- [ ] 신호→이벤트 정규화 파이프라인
- [ ] Analyst: 가설 생성 (근거 + 신뢰도 + 출처 인용)
- [ ] Skeptic: 반대 근거 검증
- [ ] 신뢰도 스코어링

**리스크 & 실행**
- [ ] 결정론적 리스크 엔진 (포지션 사이징, 가드레일)
- [ ] 하드 가드레일: 종목당 한도, 총 노출 한도, 일일 손실 한도, 손절/익절
- [ ] 브로커 어댑터 (페이퍼 트레이딩 우선)
- [ ] 주문 실행 & 체결 추적

**관측성 (Observability) — 최우선**
- [ ] 모든 결정의 감사 로그 (신호→가설→결정→체결 전체 체인)
- [ ] 자연어 근거 + 인용 출처 저장
- [ ] 실시간 대시보드 (포지션, PnL, 최근 결정과 근거)
- [ ] Kill switch (즉시 전량 청산 + 정지)

**회고 & 메모리**
- [ ] 포지션 종료 시 자동 사후 분석
- [ ] 장기 교훈 메모리 (벡터DB)

### 4.2 확장 (P2–P3, 있으면 좋음)
- [ ] 백테스팅 엔진 (과거 뉴스+가격 리플레이)
- [ ] 온라인 신뢰도 캘리브레이션 (예측 적중률 추적 → 신뢰도 보정)
- [ ] 다중 자산 (크립토 24/7 — 소액 자본과 궁합 좋음)
- [ ] 섹터/상관관계 인지 포트폴리오 분산
- [ ] 회고 기반 프롬프트 자동 개선 루프
- [ ] 알림 (텔레그램/디스코드로 결정 브리핑)
- [ ] 휴먼-인-더-루프 승인 모드 (실거래 전환 시)

### 4.3 명시적 제외 (초기)
- 옵션·선물·마진, HFT, 다계좌 운용, 소셜 신호 자동 리트윗/게시

### 5.1 컴포넌트 다이어그램

```
┌──────────────────────────────────────────────────────────────────┐
│                        데이터 수집 계층                             │
│  ┌────────┐  ┌────────┐  ┌────────┐  ┌──────────┐                 │
│  │ News   │  │  X     │  │ Reddit │  │ 가격 피드 │                 │

│  포지션 스토어 │ 감사 로그(DB) │ 벡터 메모리 │ 대시보드 │ Kill Switch│
└──────────────────────────────────────────────────────────────────┘
```

### 5.2 데이터 플로우 (한 사이클)
1. 수집 워커가 뉴스/소셜/가격을 폴링·스트림 → 원본 저장
2. 신호 처리기가 필터·정규화 → **이벤트** 생성 → 큐에 발행
3. Analyst가 이벤트 소비 → 조사(툴 사용) → 가설 생성
4. Skeptic이 가설 반박 → 신뢰도 조정
5. Risk Manager가 사이징 + 가드레일 검사 → 승인/거부
6. Trader가 브로커로 주문 → 체결 기록
7. 포지션 모니터가 손절/익절/시간 조건 감시
8. 종료 시 Reviewer가 회고 → 교훈을 메모리에 저장
9. 모든 단계가 감사 로그 + 대시보드에 반영

### 5.3 배포/런타임
- **초기:** 단일 컨테이너(모놀리스) + 스케줄러. 소액·저빈도라 과설계 금지
- **큐:** 초기엔 인메모리/경량 큐(Redis 등), 확장 시 분리
- **상태 저장:** 관계형 DB(포지션·주문·감사) + 벡터DB(메모리)
- **비밀 관리:** API 키는 환경변수/시크릿 매니저. 절대 리포 커밋 금지

## 7. 리스크 관리 (생존이 최우선)

$10–20에서는 **"많이 버는 것"보다 "안 죽는 것"** 이 전부다.

### 7.1 하드 가드레일 (LLM이 뒤집을 수 없음)
- **종목당 최대 노출:** 총자본의 X% (예: 20–25%)
- **총 노출 한도:** 현금 비중 최소 유지 (예: 상시 20%+ 현금)
- **일일 최대 손실:** -Y% 도달 시 당일 매매 중단
- **최대 낙폭(MDD) 서킷브레이커:** -Z% 도달 시 전량 청산 + 정지
- **손절/익절:** 모든 포지션에 진입 시점에 필수 설정
- **최소 주문 크기 / 수수료 인지:** 수수료가 기대수익을 먹으면 진입 금지

### 7.2 포지션 사이징
- **분수 켈리(Fractional Kelly):** 에이전트의 신뢰도·기대엣지 → 켈리 비율의 1/4~1/2만 사용
- 신뢰도 낮으면 진입 안 함(관망도 액션이다)
- **신뢰도 캘리브레이션:** 에이전트가 "0.7 확신"이라 했을 때 실제 적중률을 추적 →
  과신하면 자동 디스카운트

### 7.3 실행 리스크
- 슬리피지·유동성: 저유동성 종목 회피
- 소셜 신호의 함정: **펌프앤덤프/시세조작 패턴 탐지 → 자동 배제**
- 뉴스 지연: 이미 가격에 반영된(뒷북) 신호 필터

### 7.4 안전장치
- **Kill Switch:** 사람이 언제든 전량 청산 + 정지
- **페이퍼 우선:** 실거래 전 최소 4주 페이퍼 검증 통과 의무
- **휴먼-인-더-루프:** 실거래 초기엔 임계 금액 이상 주문 사람 승인

## 8. 백테스팅 & 평가

### 8.1 백테스트 원칙
- **룩어헤드 편향 방지:** 시점 t의 결정엔 t 이전 데이터만. 뉴스 타임스탬프 엄격 정합
- **수수료·슬리피지 반영:** 소액에선 이게 승패를 가름
- **페이퍼 = 프리프로덕션:** 실시간 페이퍼가 최종 리허설

### 8.2 평가지표
| 지표 | 의미 |
|------|------|
| 총수익률 / vs SPY | 벤치마크 대비 |
| Sharpe / Sortino | 리스크조정수익 |
| 최대낙폭 (MDD) | 최악의 손실 구간 |
| 승률 & 손익비 | 전략 특성 |
| **신뢰도 캘리브레이션** | 에이전트 자기평가의 정확도 (핵심) |
| 결정 지연 | 신호→주문 시간 |

> 수익률만 보지 않는다. **에이전트의 판단이 얼마나 잘 캘리브레이션 되어 있는가**가
> 장기 신뢰의 척도다.

| 마일스톤 | 산출물 | 완료 기준 |
|----------|--------|-----------|
| **M0 기획** | 본 문서 + 데이터소스/브로커 확정 | 리뷰 승인 |
| **M1 데이터 골격** | 수집기 + 신호 정규화 + 감사로그 스켈레톤 | 이벤트가 큐에 흐름 |
| **M2 에이전트 코어** | Analyst+Skeptic+가설 로그 | 근거 있는 가설 생성됨 |
| **M3 리스크+페이퍼** | 리스크 엔진 + Alpaca 페이퍼 실행 | 페이퍼 매매 체결·기록 |
| **M4 관측성** | 대시보드 + Kill switch + 회고 | 결정 전 과정 추적 가능 |
| **M5 페이퍼 검증** | 4주 실시간 페이퍼 운용 | 지표 리포트, MDD 통제 |

| **M7 학습 루프** | 캘리브레이션 + 회고 기반 개선 | 엣지 통계 검증 |

## 10. 리스크 & 오픈 이슈

**기술/운영 리스크**
- LLM 환각 → 근거 없는 매매 위험 → *Skeptic + 결정론적 가드레일로 방어*
- API 비용 (특히 X API 티어) → *비용 상한, 캐싱, 저빈도 폴링*
- 데이터 지연/누락 → *뒷북 신호 필터, 다중 소스 교차검증*
- 소셜 조작(봇 세력) → *봇 탐지, 급증 이상치 검증*

**법률/규제 (반드시 확인)**
- 실거래 = 실제 금융 활동. **거주 관할의 증권/세무 규정 준수 필요**
- 자동매매·API 트레이딩에 대한 브로커 약관 확인
- 시세조작 신호 추종은 법적 문제 소지 → 명시적 금지
- ⚠️ *본 프로젝트는 개인 실험/연구 목적. 투자 조언 아님. 손실 책임은 운용자.*

**열린 결정 사항 (사용자 확인 필요)**
1. 자산군: 미국 주식만? 크립토 포함? (크립토는 24/7 + 소액 친화)
2. 자율성 수준: 완전 자율 vs 휴먼 승인 (초기 권장: 페이퍼는 자율, 실거래는 승인)
3. X API 유료 티어 예산 확보 여부
4. 운용 시간대·빈도 (실시간 vs 하루 N회 배치)
